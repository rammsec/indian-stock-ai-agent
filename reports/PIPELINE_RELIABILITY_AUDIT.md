## Part I — GitHub Actions Pipeline Reliability Audit (`Step 8`)

### 1. Inspection across the 13 Reliability Dimensions

| Dimension | Current Implementation in `.github/workflows/daily_nse_research.yml` | Risk Level | Audit Findings & Evidence |
| :--- | :--- | :--- | :--- |
| **1. Scheduled Triggers** | Two weekday crons: `30 3 * * 1-5` (03:30 UTC / 09:00 IST pre-market) and `0 13 * * 1-5` (13:00 UTC / 18:30 IST post-market), plus `workflow_dispatch`. | **HIGH** | GitHub Actions scheduled workflows suffered **~8.5-hour runner queue delays** on both `2026-11-17` (run `44180088619`, 13:00 UTC cron started at `21:27:57Z` / `02:57 IST`) and `2026-11-18` (run `44300078913`, 03:30 UTC cron started at `12:02:05Z` / `17:32 IST`). |
| **2. Market-Session Conditions** | Step `calendar_check` calls `is_nse_trading_day()` using `datetime.now(IST_TZ).date()` at runner start time. And `resolve_nse_session()` (`forward_validation.py:68`) classifies `PRE_MARKET` / `INTRADAY` / `POST_MARKET` from wall-clock time. | **HIGH** | When the 13:00 UTC post-market cron is delayed past midnight IST (as in run `44180088619` at `03:00 IST`), `is_nse_trading_day()` evaluates the **next** calendar day (which would skip Friday post-market runs delayed into Saturday!), and `resolve_nse_session()` mislabels the post-market run as `PRE_MARKET`. Conversely, the delayed 03:30 UTC pre-market run `44300078913` ran at `17:32 IST` and was mislabelled `POST_MARKET`. |
| **3. Data Collection Stages** | Pre-market branch (`github.event.schedule == '30 3 * * 1-5'`) runs `run_phase5_intelligence_pipeline(use_network=True, persist=True)`. Post-market branch runs Phases 1–5 (`run_phase1_foundation.py` → `generate_static_data.py` → `run_phase2_features.py` → `run_phase3_backtest.py` → `run_phase4_corporate_intel.py` → `run_phase5_experiments.py` → `run_forward_validation.py`). | **MEDIUM** | When the pre-market cron runs late (after `09:15 IST`), it records a snapshot with `observation_date = yesterday` (`from latest_predictions.json`) but `prediction_timestamp >= today's open`, creating look-ahead-contaminated (`INVALID`) or post-close (`HISTORICAL`) snapshots. |
| **4. Data Persistence** | Parquet writes use `atomic_write_parquet_table` (`duckdb_store.py:155`) via `.tmp` + `os.replace`. | **LOW** | Atomic file replacement prevents half-written Parquet files, though `paper_trades.parquet` accumulates legacy `action="REJECTED"` and duplicate `SIGNAL_RECEIVED` rows across runs. |
| **5. Duplicate Handling** | `deduplicate_forward_predictions` keys on `(symbol, observation_date, nse_session)`. `prediction_log.parquet` keys only on `prediction_id` (`{sym}_{obs}_{model}_{ver}_{run_tag}`). | **HIGH** | Same-date snapshots across different `nse_session` values (`POST_MARKET`, `INTRADAY`, `PRE_MARKET`) remain marked `is_duplicate_run = False`, doubling canonical counts (`20` instead of `10`), while `prediction_log.parquet` has zero deduplication across re-runs (`60` evaluated rows for `15` stocks on `2026-11-16`). |
| **6. Test Execution** | Pre-market runs 3 test files (`test_phase5_news_intel.py`, `test_phase5_3_forward_validation.py`, `test_frontend_contract.py`); post-market runs `pytest -v`. | **MEDIUM** | Running `pytest -v` in the post-market workflow executes live integration tests that overwrite `data/raw/nse_bulk_block/{bulk,block}_latest.csv` in the working tree right before `git add`. |
| **7. Automatic Commits** | `git add data/processed/ data/features/ data/predictions/ data/backtests/ docs/` followed by `git commit ... [skip ci]` and `git push origin main`. | **MEDIUM** | Direct push to `main` with no `git pull --rebase origin main` before `git push` can fail if another workflow or manual commit lands while the 10-minute job is running. |
| **8. Workflow Concurrency** | **No `concurrency:` block** is defined in `.github/workflows/daily_nse_research.yml`. | **HIGH** | A severely delayed pre-market run and a post-market run (or manual `workflow_dispatch`) can execute concurrently, causing race conditions and push conflicts on `main`. |
| **9. Failure Handling** | Default bash `set -e` in multi-line `run:` steps, but `pipeline.py` and collectors catch broad exceptions and continue with fallback defaults. | **MEDIUM** | If `latest_predictions.json` is missing or corrupt, `_load_latest_quant_map` silently falls back to `{}` and `"Sideways"`, publishing `UNAVAILABLE` outlooks without failing the workflow step. |
| **10. Error Visibility** | Warnings are appended to `data_quality_warnings` inside JSON payloads, not surfaced as GitHub Actions annotations (`::warning::` / `::error::`). | **LOW** | Workflow run appears green on GitHub Actions even when 18–26 news items are quarantined or Nifty 50 benchmark lookup returns `UNAVAILABLE`. |
| **11. Data Refresh Timestamps** | `phase5_intelligence.json` captures `now_iso = datetime.now(IST_TZ).isoformat()` at the **beginning** of `run_phase5_intelligence_pipeline` (`pipeline.py:56`) and assigns it to both `generated_at` and `latest_prediction_at`. | **MEDIUM** | News collection (`collect_all_pilot_news`) runs *after* `now_iso` is captured, so 60 published timeline events have `collection_timestamp` ~13.8s *after* `latest_prediction_at`. |
| **12. Stale Published JSON Risk** | Pre-market branch does **not** run `run_phase3_backtest.py`; it reuses `data/predictions/latest_predictions.json` from the previous post-market run (`14.54h` old in run `44300078913`) while stamping `stocks[*].observation_date = today`. | **MEDIUM** | Dashboard displays `observation_date = 2026-11-18` on stock cards whose quantitative probabilities (`prob_next_day_up`, `prob_5d_up`, `prob_10d_up`) were computed on `2026-11-17`. |
| **13. Partial Failure → Apparent Success** | `build_github_pages.py` copies whatever JSON files exist in `data/predictions/` and `docs/data/`. | **MEDIUM** | If news RSS feeds time out or Nifty 50 lookup fails (`NIFTY_50` vs `"NIFTY 50"`), the pipeline still exits `0`, passes tests, and deploys partially degraded JSON to GitHub Pages. |

### 2. Recommended Pipeline Remediations (Post-Freeze)
1. **Add top-level `concurrency` control:**
   ```yaml
   concurrency:
     group: nse-quant-pipeline-${{ github.ref }}
     cancel-in-progress: false
   ```
2. **Pass explicit schedule identity (`WORKFLOW_SESSION=PRE_MARKET` vs `POST_MARKET`)** via environment variables instead of inferring `nse_session` from wall-clock time (`resolve_nse_session`).
3. **Add a pre-open cutoff guard for the pre-market job:** if GitHub Actions delays the `03:30 UTC` pre-market runner until `>= 09:15 IST`, skip recording a prospective snapshot for that morning's open (or explicitly flag it as `INTRADAY` non-prospective).
4. **Anchor `calendar_check` to the target market date** rather than `datetime.now(IST_TZ).date()` when the post-market job starts after `00:00 IST`.

## Part II — Dashboard Reporting Review (`Step 9` — Recommendations Only)

Inspection of `docs/index.html` (`renderPhase5Intelligence` at L5691–5868, `renderForwardValidation` at L5872–6015, and Executive Research Report at L2985–3070) against the 10 reporting clarity criteria:

| Criterion | Current Dashboard Behaviour (`docs/index.html`) | Audit Assessment & Recommendation |
| :--- | :--- | :--- |
| **1. Historical Data vs. 2. Prospective Forward Observations** | `fv-distinction-note` (L5880) displays static text stating historical backtests and forward observations are separated. However, the 1D Horizon Evaluation table (L5913) presents `matured_count = 10` as purely prospective even though 5 of those 10 rows are look-ahead `INTRADAY` snapshots (`2026-11-17T10:25:29 IST`), and `phase5_intelligence` timelines mix 156 historical backfilled articles (`collection_timestamp = null`). | **Recommendation:** Add separate KPI columns/badges for **Verified Prospective (`prediction_ts < entry_open`)** vs **Post-Open / Historical Re-runs**, and badge news timeline rows as `Live Collected` vs `Historical Backfill`. |
| **3. Duplicate Records** | The Executive Report (L3035) shows `20 canonical (55 stored)`, but the main Forward Validation KPI box (L5898) shows only `Immutable Snapshots: 55` without displaying `Canonical (20)` vs `Duplicates (35)`. Meanwhile, the Phase 5 Monitoring KPI box (L5723) displays `Logged Predictions: 75` and `Evaluated Outcomes: 60` without disclosing that 45 of the 60 evaluated rows are duplicate same-day runs. | **Recommendation:** Display `Canonical / Total Stored (Duplicates)` in both KPI headers, and deduplicate `monitoring` metrics before rendering. |
| **4. Pending vs. 5. Matured Outcomes** | Forward Validation KPI (L5902) shows `Matured / Pending Outcomes: 10 / 50` (summed across 1D+5D+10D), and the horizon table shows `10 / 10` (1D), `0 / 20` (5D), `0 / 20` (10D). | **Recommendation:** Label the top-level KPI explicitly as `Outcome Rows (Across 3 Horizons: 10 Matured / 50 Pending)` so users do not confuse 60 horizon-outcome rows with 60 independent stock predictions. |
